# Дизайн: третья волна `plan_check`

Дата: 2026-09-30. Статус: реализовано — PR A (`claude/plan-check-prepare-first`, в main) и PR B (`claude/plan-check-write-path`: путь записи и определения, которые планировщик сворачивает при чтении; тела SQL-функций `public`); план — `docs/superpowers/plans/2026-09-30-19-plan-check-write-path.md` (пользователь: «давай дальше»; решения по рекомендации). Продолжение `2026-09-29-plan-check-expressions-design.md` §3.

## 1. Объём

| # | Задача | PR / ветка |

| 1 | Проверка определений представлений/правил до планирования (`PREPARE` → проверка → `DEALLOCATE` → EXPLAIN) | A — `claude/plan-check-prepare-first` |

Всё — только при `plan_check` (basic). Full и `plan_check=false` не меняются.

## 2. Порядок: определения до планирования (PR A)

- Сейчас: EXPLAIN (планировщик сворачивает IMMUTABLE-вызовы представления в константы — функция выполняется) → проверка узлов/выражений → проверка правил. Отказ приходит уже после выполнения свёрнутой функции.
- Стало, для каждого проверяемого оператора в той же транзакции: `PREPARE _pgmcp_check_N AS <оператор>` (разбор и переписывание: блокировки на представления и таблицы берутся, план не строится) → проверка правил и зависимостей (запрос по `pg_locks`, как сейчас) → `DEALLOCATE _pgmcp_check_N` → EXPLAIN → проверка узлов и выражений.
- Операторы, которые нельзя подготовить (`EXPLAIN`-обёртка, `DECLARE CURSOR`), — готовится вложенный запрос, как для EXPLAIN сейчас. `GENERIC_PLAN`-случаи (`$N`) — `PREPARE` без типов параметров выводит их сам, оператор готовится в точке сохранения (`SAVEPOINT`). Если вывод невозможен (`42P18`: `$1 IS NULL`, `pg_typeof($1)`), точка сохранения откатывается и оператор готовится ещё раз с `NULL` вместо каждого `$N` — правила читаются до EXPLAIN так же. Любая другая ошибка — отказ закрыто: ошибка Postgres (первый `PREPARE` упал не на выводе типа) или `PlanUnverifiableError` (не прошёл повтор с `NULL`, в том числе текст с `NULL` не разбирается: `($2)[1]` печатается как `NULL[1]`); EXPLAIN не выполняется.
- Имя подготовленного оператора — служебное, уникальное в транзакции; `DEALLOCATE` в `finally`. `DISCARD ALL` при возврате соединения всё равно сбросит.
- Проверить: `PREPARE` не выполняет функции (разбор/переписывание не вычисляют выражения); блокировки на представления берутся при переписывании.

## 3. Операторы и агрегаты `public` (PR A)

- Оператор без схемы в выражении плана (печатается без схемы, если виден в `search_path = public`): если оператора с таким именем и типами нет среди встроенных — это оператор `public`. Каталог: `pg_operator` в `allowed_schema` по имени (и типам, если различимы по тексту — иначе все перегрузки с этим именем) → `oprcode` → правило функций (схема `allowed_schema` — пропуск; `pg_catalog` — только из `BASIC_ALLOWED_FUNCTIONS`; иначе отказ).
- Агрегат без схемы, найденный в `allowed_schema` (`pg_proc.prokind = 'a'`): его `pg_aggregate` функции (`aggtransfn`, `aggfinalfn`, `aggcombinefn`, `aggserialfn`, `aggdeserialfn`, `aggmtransfn`, `aggminvtransfn`, `aggmfinalfn`) → правило функций.
- Один пакетный запрос на оператор (только при наличии безсхемных невстроенных имён), как для функций.

## 4. Путь записи (PR B)

- Целевые таблицы DML — отношения вне `pg_catalog`/`pg_toast`, на которые этот backend держит `RowExclusiveLock` (или сильнее) после `PREPARE`.
- Для них проверяются (через `pg_depend` на функции/операторы/типы + разбор текста определения, как у правил):
  - триггеры (`pg_trigger`, не `tgisinternal`, включённые): функция триггера — правило функций; тело — см. §5 если `sql` (триггерные функции на `sql` не бывают — PL/pgSQL: непрозрачно, но функция из чужой схемы → отказ);
  - CHECK-ограничения таблицы (`pg_constraint.contype = 'c'`, текст `pg_get_constraintdef`);
  - генерируемые колонки и значения по умолчанию (`pg_attrdef`, текст `pg_get_expr(adbin, adrelid)`);
  - выражения и предикаты индексов (`pg_index.indexprs/indpred`, текст `pg_get_indexdef`);
  - CHECK доменов колонок (`pg_constraint` доменов типов колонок, рекурсивно по базовым доменам);
  - политики RLS (`pg_policy`, `polqual`/`polwithcheck`, текст `pg_get_expr`), если RLS включён на таблице.
- Правило для текста — как для выражений плана (функции/операторы/типы, строковые типы таблиц без префикса).

## 5. Тела SQL-функций `public` (PR B)

- Функции `public`, найденные в выражениях плана, в тексте правил и в объектах §4: если `prolang` = `sql` — тело (`prosrc`, для `BEGIN ATOMIC` — `pg_get_functiondef`/`prosqlbody`) разбирается pglast и проверяется теми же правилами, включая отношения (таблицы из чужих схем и без префикса → отказ), рекурсивно, глубина ≤ 5, с защитой от циклов. Не `sql` — непрозрачно (документировать).
- `SECURITY DEFINER`-функции `public` — тело проверяется так же (права владельца делают утечку опаснее, не безопаснее).
- Реализовано (PR B): текст тела — `prosrc`, для `BEGIN ATOMIC`/`RETURN` (`prosqlbody IS NOT NULL`) — `pg_get_function_sqlbody(oid)`; тела отдаёт тот же запрос реализаций, что операторы и агрегаты (все перегрузки с именем). Функции `public` берутся из SQL агента (до `PREPARE`), выражений плана, узлов `Function Scan` `public`, текстов и `pg_depend` определений, функций операторов и агрегатов `public`, других тел. Отношения тела блокируются `PREPARE … AS SELECT FROM …` до `EXPLAIN`, и следующее чтение определений покрывает их индексы, `CHECK`, ключи секционирования, статистику и политики: таблицу, которую читает только тело встраиваемой функции, иначе блокировал бы только планировщик, свернув её индекс при `EXPLAIN`. Отказ как непроверяемое (`PlanUnverifiableError`): тело с `INSERT`/`UPDATE`/`DELETE`/`MERGE` (в том числе в `WITH`), `SELECT INTO`, `FOR UPDATE`/`SHARE` или служебной командой; `SET search_path` (`proconfig`) функции с телом `prosrc`, отличный от ровно `public`, и `SET standard_conforming_strings`, отличный от `on` (при `off` Postgres лексит тело иначе, чем pglast); цепочка глубже пяти кругов. Имя, уже спрошенное в проверке, не спрашивается снова (циклы).
- Реализовано (PR B, финальное ревью): умолчания аргументов (`pg_get_expr(proargdefaults, 0)`, строка `argument_defaults` того же запроса реализаций) каждой найденной функции `public` любого языка проверяются как текст определения — планировщик подставляет их в вызов без аргумента и сворачивает `IMMUTABLE` при `EXPLAIN`. CTE в телах и текстах определений разрешаются по области видимости `WITH` (как `parse_cte`), а не по всему тексту: одноимённая таблица в соседней ветви `UNION` проверяется.

## 6. Не входит

- Тела PL/pgSQL и других процедурных языков (в том числе триггерных функций).
- Неявное приведение к reg*-колонке (поиск по имени при планировании).
- Опорные функции классов операторов (opclass) типов `public` — функция сравнения btree, хеш-функция и прочие. Их вызывают без оператора в тексте `GREATEST`/`LEAST`, `ORDER BY`, `DISTINCT`, `GROUP BY`, `UNION`, соединения слиянием, сравнение массивов и записей; они не проверяются. Операторы, которые подставляет разбор (`BETWEEN` — `>=`/`<=` и `<`/`>`, `CASE x WHEN`, `JOIN … USING`, `NATURAL JOIN`, `x IN (подзапрос)` — `=`), в SQL агента проверяются по имени, как явные.

## 7. Тесты

- PR A: юнит — порядок вызовов раннера (`PREPARE`, запрос правил, `DEALLOCATE`, EXPLAIN); отказ по правилу — EXPLAIN не отправлялся; оператор `public` с `oprcode = pg_catalog.current_setting` → отказ; с функцией `public` → проход; агрегат `public` с `secret.f` → отказ. Интеграция: IMMUTABLE `secret.api_key()` с побочным эффектом (запись в таблицу-журнал через `dblink` невозможна — использовать `RAISE NOTICE`/счётчик в `secret`? достаточно проверить, что EXPLAIN не отправлялся: `pg_stat_statements` не нужен — юнит-уровень) — интеграция: представление с `secret.api_key()` отклоняется (как раньше); оператор `public` поверх `current_setting` в SQL агента → отказ.
- PR B: юнит на каждый объект §4 и на тела §5 (фальшивый раннер); интеграция: INSERT в таблицу с триггером `secret.audit()` → отказ; с CHECK `secret.valid(x)` → отказ; с генерируемой колонкой на `current_setting` → отказ; представление над SQL-функцией `public`, читающей `secret.t` → отказ; SQL-функция `public` над `app_t` → проход.

## 8. Изменения поведения (для заметок к PR)

- PR A: с `plan_check` определения представлений и правил проверяются до планирования — свёрнутые IMMUTABLE-функции больше не выполняются до отказа; лишние `PREPARE`/`DEALLOCATE` на оператор; операторы и агрегаты `public` на функциях чужих схем или встроенных вне basic отклоняются — в том числе операторы, которые подставляет разбор (`BETWEEN`, `CASE x WHEN`, `USING`/`NATURAL`, `IN (подзапрос)`). `EXPLAIN (GENERIC_PLAN)` с невыводимым типом параметра готовится повторно с `NULL` (ещё два запроса); если не готовится и так — `PlanUnverifiableError` вместо прежней проверки правил после EXPLAIN.
- PR B: с `plan_check` DML отклоняется, если триггеры/CHECK/генерируемые колонки/индексы/домены (`CHECK` и `DEFAULT`)/политики целевой таблицы (и её секций, наследников и таблиц с каскадным FK на неё) вызывают функции чужих схем или встроенные вне basic либо читают отношения вне разрешённого; представления и выражения, вызывающие SQL-функции `public` с такими телами, отклоняются.
- PR B, строже, чем в §4: и `SELECT` отклоняется, если `CHECK`, выражения и предикаты индексов, ключ секционирования, выражения расширенной статистики (`CREATE STATISTICS … ON (выражение)`) или политики RLS (все политики таблицы, независимо от команды и роли) заблокированной таблицы или её наследников и секций вызывают функции чужих схем или встроенные вне basic: планировщик сворачивает их уже при `EXPLAIN` (проверено живьём бросающей `IMMUTABLE`-функцией).
- PR B: тела SQL-функций `public` с изменением данных, `SELECT INTO`/`FOR UPDATE`, собственным `search_path` (кроме `public`), собственным `standard_conforming_strings` (кроме `on`) или вложенностью глубже пяти — `PlanUnverifiableError`; одна перегрузка с запрещённым телом отклоняет вызов любой перегрузки с тем же именем.
- PR B: функция `public` любого языка, до которой доходит запрос, отклоняется, если её умолчания аргументов вызывают функции чужих схем или встроенные вне basic (все перегрузки с именем, даже если вызов передаёт все аргументы). Таблица без префикса или системное отношение в теле, одноимённые CTE другой области видимости, теперь отклоняются.
- PR B: текст `PlanUnverifiableError` для определений — «the definitions of views, rules, tables or functions the query reaches cannot be verified»; чтение определений читает больше каталога (по-прежнему один запрос); отношения из текстов и тел добавляют по `PREPARE … AS SELECT FROM …` и чтение определений, вложенные тела — по запросу реализаций.
